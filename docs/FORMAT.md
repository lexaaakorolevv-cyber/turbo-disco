# JSON и часы физики

Schema 3 (загрузчик также разбирает schema 1/2), `format: "routefinder"`. Пример структуры показан ниже как описание полей; настоящий файл содержит полные массивы, а не многоточия.

| Поле | Значение |
| --- | --- |
| `environment` | Точное окружение для проверки совместимости |
| `ticks` | Число физических шагов записи |
| `outer_updates` | Число внешних обновлений игры длительностью 1/240 секунды |
| `actions` | `{ "tick": 57, "down": true, "button": 1, "player": 1 }` |
| `timings` | Для каждого физического шага: `[dt, isHalfTick, isLastTick]` |
| `trace` | Снимок до подачи ввода каждые 16 шагов и на переходе solo/dual: tick, x, y, vy, speed, size, dt, flags, player2 |
| `completed` | Кандидат достиг `PlayLayer::levelComplete()` |
| `verified_from_start` | Прошёл отдельный полный повтор в процессе, создавшем файл |
| `best_percent` | Лучший достигнутый процент, 0..100 |
| `attempts`, `search_seed`, `stop_reason` | Происхождение и причина остановки |
| `search_max_cps` | 16 — текущий поиск; 0 — ручная/историческая запись без ограничения; допустимы 1–20 |

`environment` содержит версии GD/мода/SDK/loader, платформу, ID/ревизию/версию уровня, SHA-256 level string и настроек уровня, список загруженных модов с версиями, LDM/extra LDM, настройки совместимости физики, seed игры, шаг внешних обновлений и идентификатор границы ввода.

**Физический тик здесь — положительный по dt вызов реального `GJBaseGameLayer::processCommands`**, начиная с 0 после native reset. Учитываются внутренние полушаги игры. Это не кадр рендера и не предположение «один кадр = один тик». Внешние вызовы `GJBaseGameLayer::update` выполняются фиксированно по 1/240 секунды, внутренний dt и признаки каждого шага сохраняются в `timings`. Нулевой dt не расходует тик. При воспроизведении сравнивается расписание каждого шага и вся контрольная трасса.

Событие подаётся в начале соответствующего вызова `processCommands`, до оригинального метода, через `handleButton`. Удержание продолжается до следующего события отпускания. Допускается button=1; player=1 для solo/shared-dual, player=1/2 для независимого 2-player; действия возрастают по паре (tick, player), сменяют состояние своего канала и лежат в `[0, ticks)`. Несколько ручных изменений между шагами объединяются в конечное состояние. Сторона физического ввода мыши/клавиатуры не означает второго игрока в обычном однопользовательском режиме.

В 1.1.0 контроллер корабля/волны включается только во время поиска и только после сохранённого префикса. Каждая фактическая смена состояния записывается тем же `inject → appendAction`. Удержание длительностью в несколько секунд хранится одной парой press/release. При проверке и воспроизведении контроллер не вызывается: повторяются исключительно сохранённые события. Его настройки не нужны для повторения уже записанного ввода; происхождение поиска содержит версию мода, seed и число попыток.

В 1.1.1–1.2.0 поиск использовал ограничитель CPS. В исторической 1.3.0 он был выключен: `InputPacer` в режиме 0 только считает нажатия, не задерживая ни одно изменение, включая несколько внутренних шагов одного outer update. В `actions` записываются все фактически поданные смены. `search_max_cps=0` означает отсутствие ограничения как для ручной записи, так и для автоматического поиска. Исторические значения 1–20 остаются допустимыми для чтения schema 1; они не накладывают новый фильтр при воспроизведении. Отсутствие поля означает 0. Совместимость версии мода отдельно проверяется через `environment`.

Трасса включает положение, вертикальную скорость, скорость/размер персонажа, режим, направление, gravity, grounded и dash. Допуск позиции 1e-4 игровых единиц, скоростей/размера 1e-7, dt 1e-8. Это ранний детектор рассинхронизации, **не снимок всего состояния игры**. Ни один из этих параметров не используется для телепортации или коррекции игрока.

На каждом новом запуске очищаются собственные курсоры/счётчики, очередь кнопок и записанного/replay ввода игры, отпускаются кнопки обоих PlayerObject, удаляются чекпоинты и вызывается `resetLevelFromStart`. Seed фиксируется до и после native reset. Неподдерживаемые случайные и persistent item механики отклоняются. Ввод пользователя во время поиска/повтора подавляется на `handleButton`; поэтому он не смешивается с макросом.

Перезапуск откладывается до выхода из стека `update`. В первом непроверенном успешном проходе вызов оригинального `levelComplete` подавляется, чтобы не открывать экран результата перед проверкой. Следующая попытка проходит целиком с начала; нужны совпадение расписания, трассы, количества тиков/внешних обновлений и повторный `levelComplete`. Только тогда основной JSON получает `verified_from_start: true` и вызывается обычный финал игры. Смерть, внешний reset, несовместимость или рассинхронизация не могут создать проверенное прохождение.

При загрузке флаг `verified_from_start` сбрасывается в памяти. Сохранить файл как проверенный в новом сеансе можно только после реального повторного завершения. Даже ранее проверенный макрос может перестать работать при недетерминированном уровне или стороннем изменении физики.

С 1.4.0 живой поиск использует фиксированные 16 CPS: ограничиваются только rising edges по внешним обновлениям 240 Гц, отпускание допускается на ближайшем физическом шаге без минимального hold/dwell. `search_max_cps=16` записывается как происхождение поиска. Планировщики учитывают время до нового press; повтор и проверка читают только сохранённые события.

## Сеанс поиска 1.5.0

Рядом с `<level>_<hash>.best.json` находится `<level>_<hash>.search.json` с форматом `routefinder-search-session`, schema 1. Он включает лучший Macro с environment, pending input plan, исходный seed, накопленные попытки/секунды и snapshot поиска: полное состояние mt19937_64, архив до 24 последовательностей, поколение/застой/политику/фазу, компактную очередь изменений и кэш вариантов. События во внутренних массивах представлены `[tick, down]`, P1/button1 подразумеваются.

JSON пишется через временный файл/переименование с теми же ограничениями и восстановлением `.bak`, что и макрос. `.best.json` сохраняется первым и остаётся независимым от более крупного файла сеанса. Максимальный размер 128 MiB, суммарный бюджет действий snapshot — 4×MaxTicks; выход за него сообщает ошибку сохранения сеанса, не превращая лучший макрос в успешный. Проверяются границы, порядок, булевы состояния, RNG, индексы и величины правок, проценты и размеры коллекций. Смена environment/seed/window отвергает полный сеанс.

Ни одно поле сеанса не содержит снимок физического мира. Resume повторяет pending plan с native reset. Если сохранён полный кандидат, он сначала проходит реальную проверку с начала; поле verified из файла игнорируется. Успешное сохранение проверенного основного макроса удаляет устаревший сеанс.

## Дополнения сеанса 1.6.0

`learning` — 32 корзины (8 форм × normal/mini × normal/inverted), по 7 пар `[ratio, samples]`: четыре ветви ускорения корабля, гравитация, прыжок, наклон волны. Проверяются размер, конечность, диапазон 0,65–1,35 и счётчик 0–100000.

`failures` — до 256 записей `[form, kind, x, y, vy, held, inverted, mini, count, objectSpriteID]`. Это вероятностные подсказки планировщику, без указателей на объекты или снимков игры. `pending_guidance` хранит границу передачи сохранённого ввода планировщику, в том числе после помощи игрока. При сохранении во время помощи текущий введённый префикс становится pending plan; продолжение всегда начинается с полного native reset.

Скорости объектов и предыдущие измерения не восстанавливаются: при каждой попытке собираются заново. Калибровка и память не нужны для точного повтора готового макроса, потому что повтор читает только его события, расписание и трассу; поиск при повторе выключен.

## Schema 2 и shared-dual в 1.8.0

`trace[].player2` обязательно присутствует: `null` в solo либо `{x,y,vy,speed,size,flags}` активного второго персонажа. Bit 12 флагов P1 означает dual; наличие P2 обязано ему соответствовать. Переходы дополнительно записываются вне регулярного интервала 16 тиков. Повтор сравнивает присутствие и координаты/скорость/размер/флаги обоих игроков с теми же допусками. Отсутствующий P2 или перенос перехода обнаруживается как рассинхронизация.

`environment.physics.input_mode` = `single-button/native-shared-dual`, `dual_trace` = true. `player=1` в actions означает общий канал: одиночный вызов `handleButton(down,1,false)` выполняет штатную маршрутизацию GD к двум персонажам в режиме без two-player. Второй искусственный вызов не добавляется. Независимые кнопки двух игроков не поддерживаются.

Сеанс по-прежнему имеет schema 1, вложенный Macro — schema 2. Дополнительное `learning_player2` содержит отдельную калибровку второго персонажа; предыдущие наблюдения обоих игроков сбрасываются на каждой попытке. Ни короткий план, ни калибровка не нужны для повтора: он читает только сохранённый ввод и проверяет расписание/обе трассы с начала.

## Schema 3 и независимый 2-player в 1.9.0

В `actions` разрешены player=1/2. На одном тике допускаются два события в каноническом порядке P1, затем P2; состояние нажатия проверяется отдельно для каждого игрока. Размер actions ограничен 2×MaxTicks, каждая пара (tick,player) уникальна. Несколько физических событий одного игрока между тиками объединяются в конечное состояние. Отпускание P1 не отпускает P2.

`environment.physics.input_mode` для независимого режима — `two-player/native-independent`, `two_player` = true. Для shared-dual сохраняется прежнее значение input_mode, `two_player` = false. Лимит search_max_cps=16 применяется отдельно к каждому каналу; проверка и воспроизведение фильтр не применяют. Поле `flip_controls` фиксирует native настройку 0010. При изменении режима/Flip Controls во время операции она останавливается.

Сеанс schema 1 теперь пишет compact actions как `[tick,down,player]`; загрузчик также понимает старые `[tick,down]` как P1. Архив, очередь таймингов, RNG, pending plan и лучший Macro сохраняют оба канала. Для незавершённого удержания release относится к своему игроку, а не к последнему событию другого канала.

P2 в trace остаётся снимком активного dual-персонажа, как в schema 2. Успешный 2-player кандидат также требует полного native повтора с начала, совпадения расписания, обоих маршрутов и levelComplete. Независимого восстановления состояния или checkpoint не добавлено.
