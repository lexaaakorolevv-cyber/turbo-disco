# JSON и часы физики

Schema 1, `format: "routefinder"`. Пример структуры показан ниже как описание полей; настоящий файл содержит полные массивы, а не многоточия.

| Поле | Значение |
| --- | --- |
| `environment` | Точное окружение для проверки совместимости |
| `ticks` | Число физических шагов записи |
| `outer_updates` | Число внешних обновлений игры длительностью 1/240 секунды |
| `actions` | `{ "tick": 57, "down": true, "button": 1, "player": 1 }` |
| `timings` | Для каждого физического шага: `[dt, isHalfTick, isLastTick]` |
| `trace` | Снимок до подачи ввода каждые 16 шагов: tick, x, y, vy, speed, size, dt, flags |
| `completed` | Кандидат достиг `PlayLayer::levelComplete()` |
| `verified_from_start` | Прошёл отдельный полный повтор в процессе, создавшем файл |
| `best_percent` | Лучший достигнутый процент, 0..100 |
| `attempts`, `search_seed`, `stop_reason` | Происхождение и причина остановки |
| `search_max_cps` | Лимит CPS при поиске (1–20); 0 для ручной записи |

`environment` содержит версии GD/мода/SDK/loader, платформу, ID/ревизию/версию уровня, SHA-256 level string и настроек уровня, список загруженных модов с версиями, LDM/extra LDM, настройки совместимости физики, seed игры, шаг внешних обновлений и идентификатор границы ввода.

**Физический тик здесь — положительный по dt вызов реального `GJBaseGameLayer::processCommands`**, начиная с 0 после native reset. Учитываются внутренние полушаги игры. Это не кадр рендера и не предположение «один кадр = один тик». Внешние вызовы `GJBaseGameLayer::update` выполняются фиксированно по 1/240 секунды, внутренний dt и признаки каждого шага сохраняются в `timings`. Нулевой dt не расходует тик. При воспроизведении сравнивается расписание каждого шага и вся контрольная трасса.

Событие подаётся в начале соответствующего вызова `processCommands`, до оригинального метода, через `handleButton`. Удержание продолжается до следующего события отпускания. В первой версии допускаются только button=1 и player=1; действия строго возрастают по номеру тика, сменяют состояние кнопки и лежат в `[0, ticks)`. Несколько ручных изменений между шагами объединяются в конечное состояние. Сторона физического ввода мыши/клавиатуры не означает второго игрока в обычном однопользовательском режиме.

В 1.1.0 контроллер корабля/волны включается только во время поиска и только после сохранённого префикса. Каждая фактическая смена состояния записывается тем же `inject → appendAction`. Удержание длительностью в несколько секунд хранится одной парой press/release. При проверке и воспроизведении контроллер не вызывается: повторяются исключительно сохранённые события. Его настройки не нужны для повторения уже записанного ввода; происхождение поиска содержит версию мода, seed и число попыток.

С 1.1.1 перед `inject` в поиске работает `InputPacer`: он объединяет запросы и допускает смену состояния только с разрешённым интервалом. Прогноз полёта заранее учитывает этот интервал. В `actions` попадают только реально поданные нажатия/отпускания, а не заблокированные запросы. `search_max_cps` — происхождение поиска, оно сохраняется при проверке кандидата и не применяется как новый фильтр при повторе. Поле необязательно для чтения schema 1, отсутствие означает 0; совместимость версии мода всё равно проверяется через `environment`.

Трасса включает положение, вертикальную скорость, скорость/размер персонажа, режим, направление, gravity, grounded и dash. Допуск позиции 1e-4 игровых единиц, скоростей/размера 1e-7, dt 1e-8. Это ранний детектор рассинхронизации, **не снимок всего состояния игры**. Ни один из этих параметров не используется для телепортации или коррекции игрока.

На каждом новом запуске очищаются собственные курсоры/счётчики, очередь кнопок и записанного/replay ввода игры, отпускаются кнопки обоих PlayerObject, удаляются чекпоинты и вызывается `resetLevelFromStart`. Seed фиксируется до и после native reset. Неподдерживаемые случайные и persistent item механики отклоняются. Ввод пользователя во время поиска/повтора подавляется на `handleButton`; поэтому он не смешивается с макросом.

Перезапуск откладывается до выхода из стека `update`. В первом непроверенном успешном проходе вызов оригинального `levelComplete` подавляется, чтобы не открывать экран результата перед проверкой. Следующая попытка проходит целиком с начала; нужны совпадение расписания, трассы, количества тиков/внешних обновлений и повторный `levelComplete`. Только тогда основной JSON получает `verified_from_start: true` и вызывается обычный финал игры. Смерть, внешний reset, несовместимость или рассинхронизация не могут создать проверенное прохождение.

При загрузке флаг `verified_from_start` сбрасывается в памяти. Сохранить файл как проверенный в новом сеансе можно только после реального повторного завершения. Даже ранее проверенный макрос может перестать работать при недетерминированном уровне или стороннем изменении физики.
